# KeyCRM webhook — план перевірки (тестовий тригер + Playwright)

Мета: перед проєктуванням Firebase Function-приймача закрити відкриті питання
про поведінку вихідних webhook'ів KeyCRM і зафіксувати реальний payload.

## Контекст

- KeyCRM має **рівно 3** webhook-події: `lead.change_lead_status`,
  `order.change_order_status`, `order.change_payment_status`.
- Підпису / секрета / HMAC / auth-заголовка **немає** (ні в тригерах, ні в API).
  URL-токен — єдиний механізм автентичності.
- KeyCRM робить **3 спроби доставки, потім кидає назавжди**. Приймач мусить
  віддати `HTTP 200`.
- Офіційний REST API (`openapi.keycrm.app/v1`) не має ресурсу підписок/webhook.
- Обрана архітектура: тонка Firebase Function-приймач у проєкті
  `tviykomplekt-88100` (там же, де `keycrmProxy`) → черга у Firestore
  (`keycrm_webhook_events`) → воркер на сервері розгрібає чергу з Meta-паузами
  30–90 с → cron-звірка як обов'язкова підстраховка.

## Відкриті питання, які закриває ця перевірка

1. **Q1** — чи шле KeyCRM webhook, коли статус міняє не ручний драг у UI, а:
   - (b) наша Playwright-автоматизація через той самий фронтенд —
     **це реальний механізм усіх `check-*`-скриптів і `move-to-reminder.js`**;
   - (c) дія іншого тригера KeyCRM («Змінити статус»);
   - (d) зовнішній REST API `PUT /pipelines/cards/{id}` (на майбутнє).
2. **Q2** — чи приземлення нової картки в першу колонку воронки рахується як
   `lead.change_lead_status`.

Заразом: зняти реальний payload (`context`-ключі), заголовки, `User-Agent`,
source IP, затримку.

## A. Підготовка — власник, вручну в KeyCRM (admin)

Службовий акаунт `tviykomplekt_auto` — роль «менеджер», у Налаштування →
Додатково → Автоматизація він не потрапляє. Тригери створює власник.

Усе робити в ізольованій воронці, **не** в бойовій «Ліди».

1. **Тестова воронка.** Створити воронку `ТЕСТ вебхук` з 3 колонками:
   `T1` (перша), `T2`, `T3`.
2. **Доступ.** Надати акаунту `tviykomplekt_auto` доступ до цієї воронки.
3. **Тригер A — головний:**
   - Подія: `Зміна статусу воронки`
   - Значення: `T1`, `T2`, `T3` (усі три)
   - Дія: `Відправити Webhook` → `POST` →
     `https://webhook.site/<WEBHOOK_SITE_TOKEN>?tag=trigger-A`
   - Один тригер ловить будь-яке переміщення в тестовій воронці, зокрема
     приземлення в `T1`.
4. **Тригер B — для перевірки «автоматизація рухає картку» (тип c):**
   - Подія: `Зміна статусу воронки`; Значення: `T2`
   - Дія: `Змінити статус` → перенести картку в `T3` (саме переміщення,
     **не** webhook)
   - Коли картка потрапляє в `T2`, Тригер B сам пересуває її в `T3`.
     Дивимося, чи Тригер A відреагує webhook'ом на цей `T2→T3`, спричинений
     автоматикою. Циклу не буде — Тригер A лише шле webhook.
5. Передати виконавцю: точні назви воронки й колонок + їх `status_id`
   (видно в URL / DevTools).

## B. webhook.site — підготовка

- Токен `<WEBHOOK_SITE_TOKEN>` дійсний до **2026-09-12**.
  Якщо стух / сесія пізніше — регенерувати:
  `curl -X POST https://webhook.site/token`, оновити URL у Тригері A.
- Дашборд: `https://webhook.site/#!/<WEBHOOK_SITE_TOKEN>`
- За замовчуванням віддає `200` → ретраїв KeyCRM не буде (ок для основних
  тестів; перевірка ретраїв — опційна, п. E).

## C. Playwright-сесія — тест-кейси

Порядок для кожного: виконати дію → **записати точний час (wall-clock)** →
перевірити дашборд webhook.site → зіставити доставку за часом і `tag`.

Селектори / патерни брати з наявних скриптів: `collect-leads.js` (відкриття
воронки), `move-to-reminder.js` та `check-lead-notifications.js` (клік по
контролу зміни статусу / drag картки).

| #   | Дія | Що доводить | Очікування |
|-----|-----|-------------|------------|
| 0. Recon | Відкрити воронку `ТЕСТ вебхук`, скріншот колонки `T1` + зберегти HTML контролу «+ Додати картку» в `output/debug/` | потрібні селектори | — |
| TC1 | Створити нову картку прямо в `T1` | **Q2** | доставка `event=lead.change_lead_status`, `context.status_id`=`T1` |
| TC2 | Перемістити картку `T1 → T2` через UI (реальний механізм `check-*`-скриптів) | **Q1 (b)** | доставка на переміщення |
| TC3 | `T3 → T1` (перезарядка), потім знову `T1 → T2` | стабільність + чистий payload переходу; **запускає Тригер B** | доставка на `T1→T2` |
| TC4 | Після TC3 картка через Тригер B автоматично поїде `T2 → T3`. Зачекати ~30 с, оновити дашборд | **Q1 (c)** | доставка `T2→T3` є / немає — обидва результати цінні |
| TC5 *(опційно)* | Змінити статус через REST API `PUT /pipelines/cards/{id}` (потрібен `KEYCRM_API_KEY` — у Firebase config, не локально; власник тимчасово кладе в `.env`) | **Q1 (d)** | доставка є / немає |

## D. Що зняти з КОЖНОЇ доставки (webhook.site → Raw)

Зберігати в репо: `docs/keycrm-webhook-samples/<event>__<tc>.json` (тіло) +
`<event>__<tc>.headers.txt` (заголовки).

- **Тіло** — повний JSON: усі ключі `context`, типи; чи є
  `contact_id` / `client_id`, `manager_id`, `pipeline_id`, timestamps,
  `grand_total` (для order-подій).
- **Заголовки** — усі: `User-Agent` (очікуємо `keyCRM webhooks v1.0`),
  `Content-Type`, будь-що на `X-*` / `Signature` (очікуємо, що немає —
  фіксуємо факт).
- **Source IP** — webhook.site показує IP відправника. Зібрати всі унікальні
  → сід для IP-allowlist приймача.
- **Затримка** — час від дії (наш запис) до доставки.

## F. Прибирання

1. Playwright: видалити тестові картки (видалення картки воронки в ролі
   менеджера має бути доступне — на відміну від видалення клієнта; якщо ні —
   перенести в архівний / програний статус).
2. Власник: вимкнути / видалити Тригери A і B; видалити тестову воронку;
   прибрати `KEYCRM_API_KEY` з локального `.env`, якщо додавали для TC5.

---

## G. Блокери / запасні варіанти

- **Сесія мертва.** Якщо `storage-state.json` не живий — перший крок сесії
  `npm run login`. Якщо падає з «Password is incorrect» (історія в README
  `keycrm-leads-classifier`) — власник спершу звіряє пароль `tviykomplekt_auto`
  в `.env`. Блокер для всієї сесії.
- **Менеджер не дістає воронку / не може створити картку.** Fallback: власник
  робить переміщення вручну, виконавець лише знімає payload. Тоді доведено
  «ручний драг» (тип a); Playwright (тип b) йде тим самим фронтендом — сильний,
  але не 100% доказ. Краще все ж зробити TC1–TC3 через Playwright.
- **Створення картки через UI не піддається** (невідомі селектори). Fallback
  для TC1: власник створює картку в `T1` вручну поки виконавець дивиться
  дашборд; або TC5-шлях (`POST /pipelines/cards`).
