# Покращення адмінки для менеджерів — аналіз і план

**Статус:** план, нічого з цього ще не реалізовано. Відповіді на відкриті
питання зафіксовані 2026-09-11 у розділі «Ухвалені рішення» наприкінці.
**Дата аналізу:** 2026-09-11. Посилання на рядки актуальні на комміт `d65774a`.

Мета: менеджери без технічних знань мають керувати вітриною самостійно і
безпечно. Онлайн-оплати поки немає — заявки йдуть менеджеру, оплату й бронь він
узгоджує сам.

---

## Частина 1 — як воно працює зараз

### 1. Бейдж NEW

За датою створення в KeyCRM, вікно 14 днів. Не «перші N товарів», не за ID.

- `services/keycrm.ts:6` — `const NEW_WINDOW_DAYS = 14`
- `services/keycrm.ts:211` — `isNew: isWithinDays(kc.created_at, NEW_WINDOW_DAYS)`
- `services/keycrm.ts:157` — сама функція порівняння дат
- `App.tsx:935` — рендер бейджа

Значення захардкожене в бандлі, керування з адмінки немає — зміна вимагає білда
й деплою. У формі легасі-товару є чекбокс `isNew`, але сайт ту колекцію не
читає, тож він ні на що не впливає.

### 2. Hero

Сайт читає `settings/site_content` (`App.tsx:185-197`) і мержить поверх
`DEFAULT_SETTINGS` (`App.tsx:59-64`).

Документ `settings/site_content` у Firestore **існує, але не має жодного поля**
(створений 2025-12-06, оновлений 2025-12-07). Саме тому форма в адмінці порожня,
а hero береться цілком із захардкодженого `DEFAULT_SETTINGS`; фон —
`/hero-options/IMG_2275.jpg` з `public/`.

**Що станеться при «Зберегти налаштування» з порожніми полями.** Адмінка бере
`.value` кожного інпута і пише через `setDoc(..., { merge: true })`. `merge: true`
захищає лише *інші* поля документа — ці поля записуються, просто порожніми
рядками. Далі `{ ...DEFAULT_SETTINGS, ...data }` на сайті: порожні рядки
перетирають дефолти.

- Банер не зітреться — на рендері є фолбеки `||`: heroTitle (`App.tsx:812`),
  heroSubtitle (`:809`), heroDescription (`:816`), heroBackgroundUrl (`:194`, `:775`).
- **`logoText` фолбека не має.** Використовується в шапці (`:752`), заголовку
  підвалу (`:1042`) і копірайті (`:1070`). Одне порожнє збереження зітре назву
  бренду з шапки й підвалу. Найгостріша пастка для менеджера — спрацює з першого дня.

### 3. «Додати новий товар»

Пише у Firestore-колекцію `products` (`admin.html:918` addDoc, `:922` updateDoc),
картинки — у Storage `products/`.

Сайт цю колекцію **не читає**. Імпортований у `App.tsx` `PRODUCTS` — статичний
масив із `constants.ts`, задіяний лише як офлайн-фолбек, коли KeyCRM недоступний
(`App.tsx:275, 279`).

Чи є там живі товари — ззовні не перевірити: rules дозволяють читати `products`
лише авторизованим. Дивитись у адмінці (легасі-таблиця `admin.html:791` зливає
Firestore-товари зі `STATIC_PRODUCTS`) або в консолі Firestore.

### 4. Таблиця розмірів на сайті

`SIZE_CHARTS` у `constants.ts:170`, вибір у `App.tsx:625-637`. Пріоритет: власний
`sizeChart` товару → `SIZE_CHARTS[sizeCategory]` → `SIZE_CHARTS['default']`.

`mapKeycrmProduct` **ніколи не ставить ні `sizeCategory`, ні `sizeChart`** (нуль
згадок у `keycrm.ts`). Тому всі без винятку товари показують
`SIZE_CHARTS['default']` — заглушку «Стандарт S / M / L» (`constants.ts:211-218`).
Категорійні таблиці leggings / top / set / bodysuit у коді існують, але недосяжні.

### 5. Заявка з кошика

**Тільки Telegram. Замовлення в KeyCRM не створюється взагалі** — проксі приймає
лише GET (`functions/index.js:42`), POST у KeyCRM немає ніде.

Шлях: `App.tsx:569` POST `/api/order` → rewrite у `firebase.json` →
`sendOrderNotification` (`functions/index.js:111`) → `api.telegram.org/sendMessage`.

Payload:

```
{ customer: { firstName, lastName, phone, city, branch },
  items: [{ title, size, color, price }],
  total }
```

У позиції немає ні `product_id`, ні `offer_id`, ні артикула — лише назва, розмір,
колір, ціна. `total` рахується на клієнті й функцією не перевіряється.

Наслідок для ручних товарів: вони й так пройдуть через заявку без змін, KeyCRM-ID
нікому не потрібен. Зворотний бік — менеджер бачить лише назву й не розрізнить дві
схожі моделі. ID варто додати разом із рештою пакета.

## Частина 2 — план

### Три наскрізні рішення

**1. Одна колекція `productSettings/{productId}`** для дрібного скалярного: бейдж,
видимість, `sizeChartId`. Зараз кожна фіча — окрема колекція і окремий `getDocs`
на старті (їх уже 4); ще три перетворять завантаження на 7 повних читань колекцій.
Медіа / відгуки / інфо про модель лишаємо як є — вони працюють і мають свій UI.

**2. `Product.source: 'keycrm' | 'manual'`**, ручні ID — рядок `m_<autoid>`. Тип
`id: number | string` це вже дозволяє, колізій з числовими KeyCRM-ID немає.

**3. Розширений payload заявки:** `productId`, `source`, `offerId?`, `isPreorder`,
`preorderEta?`, плюс заділ під майбутню оплату: `payment { status, kind, amount }`
зі значеннями-заглушками. І серверний перерахунок `total` — без нього з оплатою це
стане дірою.

### Крок 1 — безпека і найгостріша пастка · складність низька

Rules з `function isAdmin()` і масивом UID для всіх колекцій, куди пише адмінка;
читання публічних даних сайту лишається відкритим. Тут же фікс `logoText` —
фолбек на сайті плюс заборона зберігати порожній у адмінці.

Файли: `firestore.rules`, `App.tsx`, `admin.html`.

Ризик: не той UID → адмінка миттєво втрачає запис у всі колекції. Перевірити
збереження відгуку одразу після деплою, попередні rules тримати напоготові.

### Крок 2 — бейдж NEW · низька

**Автоматичного правила більше немає.** `NEW_WINDOW_DAYS` і виклик
`isWithinDays` у `mapKeycrmProduct` (`services/keycrm.ts:6, 211`) прибираються
повністю; поля `settings/catalog.newWindowDays` не буде. Бейдж ставить тільки
менеджер.

Дані: `productSettings/{id}.newBadge = { enabled: boolean, until?: string }`,
де `until` — дата у форматі `YYYY-MM-DD`.

Логіка на сайті:

```
показувати NEW  ⟺  newBadge.enabled === true
                   && (newBadge.until відсутній || сьогодні <= until)
```

За замовчуванням (немає документа або `enabled: false`) бейджа немає. Порожній
`until` означає «показувати, поки не вимкнуть».

В адмінці:

- у модалці товару — перемикач «Бейдж NEW» (вимкнено за замовчуванням) і
  необовʼязкове поле дати «NEW до дати»;
- у списку товарів — мітка «NEW» біля назви, щоб менеджер бачив, де бейдж
  увімкнений, не відкриваючи картку.

**Міграція при деплої.** Щоб вітрина не змінилась у момент релізу, товарам, які
на той час показують NEW за старим 14-денним правилом, треба разово проставити
`newBadge = { enabled: true }` (без `until` — далі менеджер вирішує сам).

Станом на 2026-09-11 це рівно 4 товари:

| KeyCRM id | Створено | Назва |
|---|---|---|
| 165 | 2026-09-10 | CF Майка нова Calm Fit |
| 164 | 2026-09-10 | CF Лосини кльош Calm Fit |
| 163 | 2026-09-09 | BL Напівкомбінезон «BALANCE» |
| 162 | 2026-09-08 | LB палацо «Naked» |

Список **перерахувати безпосередньо перед деплоєм** — за 14-денним вікном він
змінюється сам собою, і в день релізу склад майже напевно буде інший.

Файли: `types.ts`, новий `services/productSettings.ts`, `services/keycrm.ts`
(видалення правила), `App.tsx`, `admin.html`, `firestore.rules`.

Ризик мінімальний, бейдж суто візуальний. Крок заодно обкатує нову колекцію на
дешевій фічі. Єдиний момент, за яким варто простежити — щоб після видалення
`isNew` з `mapKeycrmProduct` ніде не лишилось звернень до старого поля.

### Крок 3 — таблиці розмірів · середня

`sizeCharts/{chartId}` = `{ title, columns[], rows[][] }`. Привʼязка до **9 груп
`CATEGORIES`** (рішення 2), а не до числових `category_id`:
`settings/catalog.sizeChartByGroup: { "<groupId>": "<chartId>" }`. Перевизначення
на товарі — `productSettings/{id}.sizeChartId`.

Пріоритет на сайті: товарна → групова → **загальна за замовчуванням** →
нічого. Заглушку `SIZE_CHARTS['default']` («Стандарт S / M / L») прибрати; замість
неї — справжня загальна таблиця, яку менеджер заповнює в адмінці
(`settings/catalog.defaultSizeChartId`). Якщо не заповнено жодної — ховати і
кнопку «Таблиця розмірів», і посилання з плашки інфо про модель.

**Явне «таблиця не потрібна».** Окремо від «таблиці ще немає» має бути свідоме
рішення менеджера, що товару чи цілій групі таблиця не потрібна — рукавички,
аксесуари тощо. Позначка на двох рівнях:

- товар — `productSettings/{id}.sizeChartMode: 'inherit' | 'none' | 'custom'`;
- група — `settings/catalog.sizeChartByGroup["<groupId>"] = null` як явне «не
  потрібна» (на відміну від відсутнього ключа = «ще не налаштовано»).

При `none` сайт не показує ні таблицю, ні кнопку, ні посилання з плашки інфо про
модель, і **не падає на загальну таблицю**. Значок «немає таблиці» в списку
товарів (Крок 5) для таких товарів не горить — інакше менеджер вічно бачитиме
незакритий пункт.

Термобілизна (id 116, `category_id=11`) лишається на загальній таблиці за
замовчуванням, рукавички (id 135, `category_id=12`) — кандидат на `none`.

Файли: `constants.ts`, `types.ts`, новий `services/sizeCharts.ts`, `App.tsx`,
`admin.html`, `firestore.rules`.

Ризик: якщо таблиці не заповнити, кнопка зникне всюди. Мітігація — у цьому ж кроці
одноразово засідити 4 наявні категорійні таблиці з `constants.ts` у Firestore і
завести загальну.

### Крок 4 — адмін-сесія на сайті · низька

Новий крок, витягнутий окремо, бо від нього залежать і Крок 5 (приховані товари),
і Крок 6a (чернетки). Сайт починає читати стан Firebase Auth: `getAuth` +
`onAuthStateChanged` у `App.tsx`, індикатор «режим адміна» в шапці.

**Чому це працює (рішення 5).** `admin.html` і сайт — той самий origin
(`tviykomplekt-88100.web.app`), той самий `apiKey`, той самий default-app
`[DEFAULT]`. Firebase Auth зберігає сесію в IndexedDB (`firebaseLocalStorageDb`,
ключ `firebase:authUser:<apiKey>:[DEFAULT]`), спільній для всієї origin. Тому
залогінений в `admin.html` адмін автоматично «залогінений» і для сайту — окремий
вхід на сайті не потрібен. Різниця версій SDK (адмінка 9.23 з CDN, сайт 10.8 з
npm) на формат сховища не впливає.

**Обмеження:** сесія живе в межах одного origin. Прод, `localhost:3000` і кожен
preview-канал — різні origin, сесія між ними не переноситься.

**Спосіб тестування кроків 4, 5 і 6a — логінитись в `admin.html` прямо на
preview-домені.** Preview-канал віддає і сайт, і `admin.html` з **того самого**
домену (`...--model-info-<hash>.web.app`), тому щойно адмін увійшов у preview-
адмінку, сайт на preview бачить ту саму сесію. Звичний цикл «preview → тест →
прод» зберігається, просто на preview треба увійти окремо — сесія з прода туди не
переноситься.

Чи не заблокує це Authorized domains: **не має**. Цей список гейтить OAuth-потоки
(`signInWithPopup` / `signInWithRedirect`) і редірект-хендлер, а адмінка
використовує лише `signInWithEmailAndPassword` — виклик Identity Toolkit, який не
перевіряє origin. Тому вхід з preview-домену має працювати без жодних змін у
консолі.

> Це висновок з аналізу, не перевірений на практиці — облікових даних адмінки в
> мене немає. Перевірка займає дві хвилини: відкрити `<preview-домен>/admin.html`
> і спробувати увійти. Якщо вхід усе ж відхилять — додати preview-домен у
> Firebase Auth → Settings → Authorized domains. URL каналу стабільний для того
> самого імені каналу (перевірено: `model-info-rh5m17ke` не змінився між двома
> деплоями), тож це разова дія на канал, а не на кожен деплой. Після завершення
> робіт запис прибрати.

Практичний наслідок: для цих кроків тримати **одне стабільне імʼя каналу**
(`model-info` або новий, але один), щоб origin не мінявся й не доводилось щоразу
логінитись наново чи правити Authorized domains.

Файли: `firebase.ts`, `App.tsx`.

### Крок 5 — видимість + індикатори заповненості · середня

«Приховати з сайту» — `productSettings/{id}.hidden` (KeyCRM не чіпаємо).
Приховані зникають з каталогу, пошуку і фільтрів для клієнтів; адмін (Крок 4)
бачить їх із міткою.

**Чесне застереження про межу захисту.** Для товарів KeyCRM «приховано» — це
рівень вітрини, а не безпеки: дані товару однаково доступні через наш власний
публічний проксі `/api/keycrm/products`. Справжня межа буде тільки в чернеток
ручних товарів (Крок 6a), де її забезпечують rules. Для поточної задачі
(прибрати товар з вітрини) цього достатньо, але називати це приховуванням від
стороннього ока не можна.

Прямих посилань на товар сьогодні не існує взагалі — у `App.tsx` немає ні роутера,
ні `URLSearchParams`, ні `window.location`; картка товару це модалка без URL. Тому
пункт «зникає з прямого посилання» поки безпредметний, а перший розбір URL у
застосунку зʼявиться аж у Кроці 6a заради перегляду чернеток.

Індикатори (рішення 7) — **5 значків**: інфо про модель, відгуки, відео, додаткові
фото, таблиця розмірів. Бейдж NEW значка не отримує. Приховані товари — сірий рядок
плюс мітка «Приховано» біля назви, не значок. Плюс фільтр «не заповнено».

Ризик видимості: приховані мають зникнути і з фасетів фільтрів, інакше зʼявиться
колір, за яким нічого не знайдеться. Фільтрувати **до** обчислення
`availableColors` / `availableSizes` / `priceBounds` (`App.tsx:400-416`).

Ризик індикаторів: значки потрібні для всіх товарів одразу, тож адмінці доведеться
читати колекції цілком одним `getDocs` замість поточного `onSnapshot` на один
документ при відкритті модалки. На швидкість вітрини не впливає.

### Крок 6 — ручні товари · висока, ділиться на три

**6a. Дані + каталог.** `manualProducts/{m_xxx}`: title, price, oldPrice,
`categoryId` (число з KeyCRM-категорій, щоб фільтр і групи працювали однаково),
description, images[], `status: 'draft' | 'announce' | 'selling'`,
`variants[{ color, size, availability: 'in_stock' | 'preorder' | 'out_of_stock', preorderEta? }]`.

Кольори й розміри (рішення 3) — **тільки вибір зі списку, без вільного тексту**:
кольори з тих, що вже є в каталозі (нормалізовані через `COLOR_ALIASES` у
`constants.ts`), розміри — фіксований XS / S / M / L / XL / XXL. Це прибирає ризик,
що в фільтрі зʼявляться «Чорний» і «чорний» як два різні свотчі.

Сайт: новий сервіс, мерж у `allProducts`; `colors` / `sizes` виводяться з
`variants`, тому фільтри каталогу працюють без правок.

**Чернетки — справжній захист (рішення 5).** Rules: читання `manualProducts`
публічне тільки для `status in ['announce','selling']`, чернетки — лише `isAdmin()`.

> **Пастка, яку легко не помітити: rules у Firestore — це не фільтр.** Якщо
> правило дозволяє читати лише не-чернетки, то `getDocs(collection(...))` без
> умови впаде цілком, а не поверне частину. Тому публічний шлях **зобовʼязаний**
> запитувати `query(collection(db,'manualProducts'), where('status','in',['announce','selling']))`,
> а адмінський — окремий незвужений запит під `isAdmin()`. Це треба закласти в
> код одразу, інакше каталог просто не завантажиться.

Ризик 429: ручні товари не торкаються `/offers`, головне загардити
`fetchOffersForProduct` по `source`, щоб `m_` ID туди не потрапив. Кеш оферів
(`sessionStorage`, `tvk_offers_variants_cache_v1`) не чіпаємо взагалі.

**6b. Кошик і заявка.** Кнопка залежить від статусу товару й доступності обраного
варіанта: В наявності → «Додати в кошик»; Під замовлення → «Передзамовити» + термін,
який вписує менеджер; Немає → «Дізнатись про надходження». Для статусу «Анонс» —
завжди «Дізнатись про надходження».

«Дізнатись про надходження» (рішення 4) відкриває **чат KeyCRM** — віджет уже
стоїть в `index.html`. Баг зі звʼязкою чат ↔ CRM виправлено підтримкою KeyCRM
11.09.2026, перевірено в обидва боки (див. `keycrm-chat-widget-investigation.md`),
тож канал робочий.

`CartItem` отримує `isPreorder`, `preorderEta`, `source`, `productId`; функція
друкує мітки «ПЕРЕДЗАМОВЛЕННЯ» і «не з KeyCRM» та термін.

Ризик: функція жорстко валідує payload і віддає 400 на відхилення. Нові поля
робити **тільки опційними**, і деплоїти **функцію першою**, сайт другим. Інакше
стара збірка в чиємусь кеші плюс нова функція = втрачені заявки.

**6c. Привʼязка до товару KeyCRM.** Перенос оверлеїв (модель / відгуки / відео /
фото / бейдж / таблиця) на KeyCRM-ID плюс `status: 'draft'` ручному — однією
`writeBatch`, щоб не було моменту з дублем на сайті. Відгуки зливати, не затирати;
показати діф перед застосуванням.

## Що може зламатись

| Що | Загроза | Як уникнути |
|---|---|---|
| Кеш оферів / захист від 429 | `m_` ID потрапить у `fetchOffersForProduct` | гард по `source`, кеш не чіпати |
| Каталог ручних товарів | rules — не фільтр, незвужений `getDocs` впаде цілком | публічний запит завжди з `where('status','in',[...])` |
| Фасети фільтрів | приховані й чернетки лишаться в списках кольорів і розмірів | фільтрувати до обчислення фасетів |
| Кольори ручних товарів | «Чорний» і «чорний» як два свотчі | тільки вибір зі списку, нормалізація `COLOR_ALIASES` |
| Заявки | нові поля → 400 від функції | функція першою, поля опційні |
| Плашки інфо про модель | ключ за URL фото | нормалізація та сама, працює як є |
| Відгуки | перенос при привʼязці затре наявні | `writeBatch` + злиття |
| Таблиця розмірів | прибрали `default` → кнопки немає ніде | засідити категорійні + загальну в тому ж кроці |
| Firestore rules | не той UID → адмінка мертва | перевірити запис одразу після деплою |
| Видалення легасі | зачепити чужі файли в Storage | список файлів до видалення, `productMedia/` не чіпати |

Кеш бандла більше не ризик — `no-cache` на HTML уже в проді (див.
`firebase.json`, `headers`).

## Дрібні задачі на потім

- **Автоматичний бейдж «Останні розміри»** із залишків KeyCRM. Свідомо не
  робимо зараз. Головна перешкода не в коді, а в даних: `quantity` у KeyCRM для
  цього магазину не означає наявність — близько 89 % реальних оферів мають
  `quantity <= 0`, хоча товар активно продається, бо фулфілмент ручний, а не
  привʼязаний до складського обліку (див. коментар у `App.tsx` біля
  `isVariantAvailable`). Тому такий бейдж зараз показував би «останні розміри»
  майже на всьому каталозі. Повертатись до задачі має сенс тільки після того, як
  залишки в KeyCRM почнуть вестись всерйоз.

- **Товари поза кнопками категорій.** `category_id=11` (Термобілизна, id 116) і
  `category_id=12` (Аксесуари, id 135) не входять у жодну з 9 груп `CATEGORIES`,
  тому в каталозі їх видно лише через кнопку «Всі» — окремої категорії для них
  немає. Треба вирішити: додати 1–2 нові групи в `CATEGORIES` чи приписати ці
  `category_id` до наявних. Зачіпає `constants.ts` і, за рішенням 2, привʼязку
  таблиць розмірів. Поки не робимо.

## Суміжне, поза цим планом

Запис у Firestore зараз дозволений будь-якому авторизованому акаунту
(`request.auth != null`), а не конкретному адміну. Оскільки `apiKey` публічний, а
провайдер Email/Password за замовчуванням дозволяє самореєстрацію, сторонній може
створити акаунт і писати в усі колекції. Крок 1 закриває наслідок; причину треба
закривати окремо — вимкнути sign-up у GCP Identity Platform → Settings → User
actions. Перевірити також Authentication → Users на незнайомі акаунти.

Це особливо важливо тепер, коли чернетки ручних товарів покладаються на
`isAdmin()` як на справжню межу захисту.
