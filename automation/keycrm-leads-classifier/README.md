# KeyCRM Leads Classifier (dry-run, етап 1: збір даних)

Автономний Playwright-інструмент для tviykomplekt.keycrm.app. Не залежить
від коду основного сайту (React/Vite/Firebase) і не імпортує з нього нічого.

Етап 1 (поточний): лише збір переписки з перших 5 карток у колонці
"Відхилити лід" — без AI-класифікації і без жодних кліків по кнопках
зміни статусу.

## Встановлення

Виконано автоматично при створенні інструмента:
- `npm install` (playwright, dotenv)
- `npx playwright install chromium`

## Налаштування

1. Скопіюй `.env.example` у `.env`:
   ```
   cp .env.example .env
   ```
2. Заповни `KEYCRM_EMAIL` та `KEYCRM_PASSWORD` реальними даними для входу
   в tviykomplekt.keycrm.app. Файл `.env` вже додано в `.gitignore`
   (і кореневий `.gitignore` теж його ігнорує) — в git він не потрапить.

## Запуск

Перший запуск — логін і збереження сесії (щоб надалі не логінитись знову):

```
npm run login
```

Це створить `storage-state.json` (теж у `.gitignore`) з cookies/сесією.

Далі — збір діалогів:

```
npm run collect
```

Результат: `output/leads_dialogs.json` — масив об'єктів
`{ cardIndex, customerName, messages: [{sender, text}], rawText }`.

За замовчуванням браузер запускається у видимому режимі (headed), щоб
можна було спостерігати за процесом і за потреби втрутитись. Щоб
запустити без вікна браузера:

```
HEADLESS=true npm run collect
```

## Якщо селектори не спрацьовують

Скрипт написаний без можливості інспектувати реальний DOM KeyCRM
(вхід виконується лише з реальними credentials користувача). Селектори
в `collect-leads.js` (константа `SELECTORS`) — best-effort і можуть
потребувати коригування під фактичну розмітку.

При помилці на конкретній картці скрипт зберігає скріншот і HTML
модалки в `output/debug/` (наприклад `card-2-error.png/.html`) — це
найшвидший спосіб побачити фактичну структуру й поправити селектор.

## Безпека

- Реальні `.env` та `storage-state.json` НЕ комітяться (гітігнорені).
- Скрипт збору НІКОЛИ не клікає кнопки зміни статусу ліда — тільки
  відкриває картку, читає дані та закриває через X / Escape.

## Якщо сесія раптово протухла повністю (і authToken, і refreshAuthToken)

Підтверджена причина (інциденти 17.08.2026 та 24.08.2026): `KEYCRM_EMAIL`
в `.env` — це особистий акаунт власниці (kondratiukristina@gmail.com), під
яким вона сама заходить у KeyCRM через звичайний браузер. KeyCRM, схоже,
дозволяє лише ОДНУ активну сесію на акаунт — коли вона логіниться вручну,
сервер миттєво інвалідовує стару серверну сесію автоматизації, і обидва
токени (`authToken` і `refreshAuthToken`) одночасно стають непридатними
(POST /auth/refresh повертає 400). Це НЕ звичайне TTL-протухання і НЕ
проблема частоти heartbeat-крону (`keep-session-alive.js`) — навіть
щохвилинна перевірка не врятує, бо розрив стається миттєво в момент
чужого логіну, а не поступово.

Симптом: `output/keep-session-alive.log` показує `POST /auth/refresh
повернув HTTP 400` для ОБОХ проєктів одночасно, після довгого періоду
стабільної роботи. `journalctl -u crond` при цьому чистий (сам крон не
пропускав запуски) — шукати причину на цьому сервері (reboot, зсув
годинника) марно, вона зовнішня, на боці KeyCRM.

Що робити зараз (тимчасово, поки немає окремого акаунта):
1. Зайти в KeyCRM (можна тим самим `npm run login`, або вручну зібрати
   `authToken`/`refreshAuthToken` з localStorage DevTools) і оновити
   `storage-state.json` свіжою парою токенів.
2. Перевірити живучість: `GET /auth/profile` з новим `authToken` має
   повернути 200 (див. `isTokenAlive` у `../refresh-session.js`).

Правильне довгострокове рішення: завести ОКРЕМИЙ службовий акаунт у
KeyCRM спеціально для автоматизації (Налаштування → Доступ →
Користувачі → «Додати користувача»), з окремою урізаною роллю
(Налаштування → Доступ → Ролі → «Додати роль» — можна обмежити лише
доступом до лідів, без прав власника/адміністратора). Це повністю
усуває конфлікт сесій, бо кожен акаунт має свою окрему сесію на боці
KeyCRM. На момент написання цей акаунт ще НЕ створено — `.env` досі
вказує на особистий акаунт власниці.
