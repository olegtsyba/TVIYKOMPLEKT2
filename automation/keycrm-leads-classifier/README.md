# KeyCRM Leads Classifier (dry-run, етап 1: збір даних)

Автономний Playwright-інструмент для tviykomplekt.keycrm.app. Не залежить
від коду основного сайту (React/Vite/Firebase) і не імпортує з нього нічого.

Етап 1 (поточний): лише збір переписки з перших 5 карток у колонці
"Відхилити лід" — без AI-класифікації і без жодних кліків по кнопках
зміни статусу.

## Встановлення

Виконано автоматично при створенні інструмента:
- `npm install` (playwright, dotenv)
- `npx playwright install chromium`

## Налаштування

1. Скопіюй `.env.example` у `.env`:
   ```
   cp .env.example .env
   ```
2. Заповни `KEYCRM_EMAIL` та `KEYCRM_PASSWORD` реальними даними для входу
   в tviykomplekt.keycrm.app. Файл `.env` вже додано в `.gitignore`
   (і кореневий `.gitignore` теж його ігнорує) — в git він не потрапить.

## Запуск

Перший запуск — логін і збереження сесії (щоб надалі не логінитись знову):

```
npm run login
```

Це створить `storage-state.json` (теж у `.gitignore`) з cookies/сесією.

Далі — збір діалогів:

```
npm run collect
```

Результат: `output/leads_dialogs.json` — масив об'єктів
`{ cardIndex, customerName, messages: [{sender, text}], rawText }`.

За замовчуванням браузер запускається у видимому режимі (headed), щоб
можна було спостерігати за процесом і за потреби втрутитись. Щоб
запустити без вікна браузера:

```
HEADLESS=true npm run collect
```

## Якщо селектори не спрацьовують

Скрипт написаний без можливості інспектувати реальний DOM KeyCRM
(вхід виконується лише з реальними credentials користувача). Селектори
в `collect-leads.js` (константа `SELECTORS`) — best-effort і можуть
потребувати коригування під фактичну розмітку.

При помилці на конкретній картці скрипт зберігає скріншот і HTML
модалки в `output/debug/` (наприклад `card-2-error.png/.html`) — це
найшвидший спосіб побачити фактичну структуру й поправити селектор.

## Безпека

- Реальні `.env` та `storage-state.json` НЕ комітяться (гітігнорені).
- Скрипт збору НІКОЛИ не клікає кнопки зміни статусу ліда — тільки
  відкриває картку, читає дані та закриває через X / Escape.

## Якщо сесія раптово протухла повністю (і authToken, і refreshAuthToken)

Історія (інциденти 17.08.2026 та 24.08.2026): раніше `KEYCRM_EMAIL` в
`.env` вказував на особистий акаунт власниці (kondratiukristina@gmail.com),
під яким вона сама заходила у KeyCRM через звичайний браузер. KeyCRM,
схоже, дозволяє лише ОДНУ активну сесію на акаунт — коли вона логінилась
вручну, сервер миттєво інвалідовував стару серверну сесію автоматизації, і
обидва токени (`authToken` і `refreshAuthToken`) одночасно ставали
непридатними (POST /auth/refresh повертав 400). Це НЕ звичайне
TTL-протухання і НЕ проблема частоти heartbeat-крону
(`keep-session-alive.js`) — навіть щохвилинна перевірка не врятувала б,
бо розрив стається миттєво в момент чужого логіну, а не поступово.

використовується.** Логін `tviykomplekt_auto` (email
`kopacnadezda171@gmail.com` — свідомо обрана вільна поштова адреса, не
чиясь особиста; довелось шукати готову вільну через проблему з номером
телефону при реєстрації нового Gmail) заведено спеціально для
автоматизації і прописано в `.env` обох проєктів
(`keycrm-leads-classifier` і `keycrm-client-data-extractor`) з
2026-08-24 21:06. `.env` більше НЕ вказує на особистий акаунт власниці.

Це мало повністю усунути конфлікт сесій (кожен акаунт — своя окрема
сесія на боці KeyCRM), але вже після переходу (2026-08-25, ~21:00)
стався ще один збій "обидва токени одночасно 400" — під час
розслідування виявилось, що це НЕ повторний конфлікт сесій (останній
відомий вхід під `tviykomplekt_auto` передував вікну збою), і, окремо,
що поточний пароль у `.env` сервер більше не приймає ("Password is
incorrect or user does not exists" при спробі `npm run login`). Точна
причина обох цих речей ще з'ясовується; не вважай "окремий акаунт"
панацеєю, поки причина серпневого-25 збою не підтверджена.

Симптом: `output/keep-session-alive.log` (шлях: `../output/`, спільний
для обох проєктів) показує `POST /auth/refresh повернув HTTP 400`
одночасно для обох проєктів, після довгого періоду стабільної роботи.
`journalctl -u crond` при цьому чистий (сам крон не пропускав запуски)
— шукати причину на цьому сервері (reboot, зсув годинника) марно, вона
зовнішня, на боці KeyCRM.

Що робити зараз:
1. Зайти в KeyCRM (можна тим самим `npm run login`, або вручну зібрати
   `authToken`/`refreshAuthToken` з localStorage DevTools) і оновити
   `storage-state.json` свіжою парою токенів. Якщо `npm run login`
   падає з "Password is incorrect or user does not exists" — пароль у
   `.env` розійшовся з реальним паролем акаунта `tviykomplekt_auto`,
   спочатку звір/онови його.
2. Перевірити живучість: `GET /auth/profile` з новим `authToken` має
   повернути 200 (див. `isTokenAlive` у `../refresh-session.js`).
