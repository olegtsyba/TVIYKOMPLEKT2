# KeyCRM Client Data Extractor (staged, без автозаповнення)

Автономний Playwright + Claude API інструмент для tviykomplekt.keycrm.app.
Незалежний проєкт (не ділить код з `keycrm-leads-classifier`, хоча сесія
KeyCRM спільна для всього домену).

## Задача

Коли лід переходить у статус "Замовлення сформовано", менеджер вручну
переносить дані клієнта (ПІБ, телефон, місто, відділення/поштомат Нової
Пошти) з переписки в картку покупця. Цей інструмент автоматизує збір і
перевірку цих даних — **без автозаповнення картки**, лише готує
структурований, перевірений результат для підтвердження людиною.

## Пайплайн

```
npm run login     — логін, зберігає storage-state.json
npm run collect   — Playwright: збирає переписку з карток колонки
                     "Замовлення сформовано" -> output/orders_dialogs.json
npm run extract   — Claude API: витягує ПІБ/телефон/email/місто/відділення
                     з кожного діалогу -> output/extraction_results.json
npm run validate  — GET-запити до Nova Poshta proxy API KeyCRM (без AI):
                     перевіряє місто й номер відділення
                     -> output/validation_results.json
npm run export    — читабельний звіт по кожному замовленню + зведена
                     таблиця + список того, що потребує ручної перевірки
```

## Налаштування

1. `cp .env.example .env`, заповни `KEYCRM_EMAIL`, `KEYCRM_PASSWORD`,
   `ANTHROPIC_API_KEY`.
2. `npm run login` (створює `storage-state.json`).

Форма логіну KeyCRM іноді поводиться нестабільно з Playwright — якщо
`npm run login` не спрацював, можна оновити `storage-state.json` вручну:
відкрий tviykomplekt.keycrm.app у Chrome, залогінься, у DevTools →
Application → Local Storage скопіюй значення `authToken` і
`refreshAuthToken`, встав їх у відповідні поля `storage-state.json`
(структура файлу — стандартний Playwright storageState).

## Валідація адреси — важливі нюанси

- Пошук міста (`/delivery/novaposhta/location?query=`) нечіткий і матчить
  однакові назви населених пунктів у різних областях (включно з селами,
  що мають ту саму назву, що й велике місто — наприклад є село "Київ" у
  Миколаївській обл.). Тому **навіть точний збіг по `MainDescription`**
  іноді дає кілька кандидатів.
- **Тай-брейкер за номером відділення:** якщо місто неоднозначне, але
  клієнт назвав номер відділення/поштомата — для КОЖНОГО кандидата міста
  робиться запит списку складів з фільтром по цьому номеру (`&query=`).
  Якщо номер існує рівно в одного кандидата — він автоматично обирається
  (`status: 'ok'`) з приміткою, що вибір підтверджено перевіркою номера
  (позначка `needsAttention: false` — це інформаційна нотатка, а не
  привід для ручної перевірки в export). Якщо номер існує в кількох
  кандидатів або в жодного — лишається "неоднозначно" на ручний вибір.
  На практиці це майже завжди однозначно вирішує "Київ" на користь
  справжнього міста, бо в однойменному селі номерів відділень з такими
  великими номерами просто немає.
- Пошук відділення (`/delivery/novaposhta/warehouse?location_ref=`) без
  додаткового `&query=<номер>` обрізає відповідь на 100 записів без
  пагінації — для міст з великою кількістю відділень (Київ і подібні)
  цього замало. Тому валідація номера відділення завжди робить запит з
  `query=<номер>`, а потім фільтрує на точний збіг `Number` (сам `query`
  — підрядковий пошук, тобто "250" матчить і "25018").
- Кожен виклик API зберігає сиру відповідь у `output/debug/order-N-location.json`
  і `output/debug/order-N-warehouse.json` — корисно для діагностики, якщо
  щось не збіглося.

## Селектори Playwright

`collect-orders.js` використовує ту саму kanban-дошку й модалку картки,
що й `keycrm-leads-classifier` (Element UI / Vue). Цільова колонка —
`"Замовлення сформовано"` (`data-alias="zamovlennya_sformovano"`,
підтверджено живою інспекцією DOM). Якщо селектори колись перестануть
працювати — дивись `output/debug/*-error.png/.html`, що зберігаються
автоматично при помилці на конкретній картці.

## Безпека

- `.env` та `storage-state.json` НЕ комітяться (гітігнорені).
- `collect-orders.js` тільки читає картки (відкриває/закриває модалку),
  ніколи не клікає кнопки зміни статусу чи полів картки покупця.
- Автозаповнення картки покупця в KeyCRM — окремий, пізніший етап, і в
  цьому проєкті свідомо не реалізоване.
